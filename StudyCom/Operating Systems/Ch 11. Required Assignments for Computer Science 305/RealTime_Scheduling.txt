# OS Real-Time Scheduling Project — RM / DM / EDF (Assignment 3)

## Design overview

`rts_sim3.py` is a genuine **next-event, preemptive** simulator: the clock
never advances by a fixed tick. At every step it looks only as far ahead as
the next thing that could possibly change who should be running — either a
new periodic job arriving, or the currently running job finishing — jumps
straight there, and re-evaluates. This means an arriving higher-priority job
correctly preempts a running lower-priority one on the very next loop
iteration, without the simulator ever needing to "poll" time in between.

The three policies (RM, DM, EDF) share 100% of the simulation engine — the
*only* thing that differs between them is a three-line priority function:

```python
def priority_key_rm(job, proc_by_id):   return (proc_by_id[job.pid].period, job.pid)
def priority_key_dm(job, proc_by_id):   return (proc_by_id[job.pid].rel_deadline, job.pid)
def priority_key_edf(job, proc_by_id):  return (job.abs_deadline, job.pid)
```
RM and DM are **fixed-priority**: a process's priority never changes.
EDF is **dynamic**: each individual *job* (one periodic release) carries its
own absolute deadline, and the ready job with the soonest one always wins —
this is why EDF needs the general "compute priority per job", not just
"compute priority per process".

## A required design decision: service (execution) time

The assignment's input table only lists Process Number, Arrival Time,
Relative Deadline, and Period. None of RM, DM, or EDF can actually be
simulated without also knowing how long each job runs for (usually written
`C_i`) — you cannot decide who has priority to *finish* on time, or measure
CPU load, without it. The assignment text acknowledges this gap itself
("this program doesn't specify certain service times... following are some
suggestions... in milliseconds"), so a 5th column, **ServiceTime**, was added
to the input file format, and every input file used here documents in its
own header comment exactly how that column's values were chosen and why.

The "0 to 101 / 0 to 413 / 0 to 500 ms" figures given in the prompt were
used as the **simulation horizon** (how long each policy is simulated for),
not as a per-process burst time — RM gets the shortest observation window
because it is the least capable of the three policies and tends to fail
fastest if it's going to fail at all; EDF gets the longest because it is the
theoretically strongest of the three (feasible for any workload with total
utilization ≤ 100%) and deserves the most room to prove it.

## Three test files

### 1. `sample_given3.txt` — the assignment's own worked numbers
The Process/Arrival/Deadline/Period columns are copied exactly from the
prompt; service times were synthesized as `C_i = round(0.5 * D_i)` (a
process can't sensibly need *more* time than its own deadline allows when
running alone, so this is a defensible lower-effort default). This happens
to produce a heavily **overloaded** system — total utilization ≈ 138% — so
it serves as the clean "this cannot possibly be scheduled" baseline.

**Result: all three policies fail almost immediately**, and identically —
first miss at t = 10 (process 3) in every case. This is expected and
correct: when total utilization exceeds 100%, *no* scheduling algorithm
(however smart) can meet every deadline — RM, DM, and EDF only differ in how
gracefully or how differently they fail, never in whether an overloaded
system succeeds.

| | RM | DM | EDF |
|---|---|---|---|
| Feasible until | t=10 | t=10 | t=10 |
| First miss | Process 3 | Process 3 | Process 3 |
| Total misses (over its horizon) | 9 | 37 | 117 |
| CPU utilization | 100% | 100% | 100% |

### 2. `custom_input3.txt` — our own set, total utilization exactly 1.0
Five tasks (periods 20/25/30/40/50, one with a constrained deadline < period)
chosen so `sum(C_i / T_i) = 1.00` exactly — the theoretical boundary at
which EDF is *just barely* still guaranteed feasible (EDF is feasible iff
utilization ≤ 100%, a necessary-and-sufficient condition), while RM's
classical Liu & Layland sufficient bound for 5 tasks (≈ 74.3%) is
comfortably exceeded.

**Result: matches theory precisely.**

| | RM | DM | EDF |
|---|---|---|---|
| Feasible until | t=35 (Process 4 misses) | t=35 (Process 4 misses) | **entire 500-unit window** |
| Total misses | 3 | 9 | **0** |
| CPU utilization | 100% | 100% | 100% |

RM and DM fail at the *same* point here because, for this particular task
set, their priority orders happen to coincide (periods and relative
deadlines are ranked the same way across all 5 processes) — a useful,
honest result in itself, but it doesn't showcase what's supposed to be
different about DM, which is why a second custom file was built.

### 3. `custom_input2_3.txt` — engineered to make RM and DM genuinely diverge
Process 1 (period 10, deadline 9, service 5) and Process 2 (period 12,
deadline 6, service 2) are constructed so their **period order and deadline
order are opposite**: RM (period-based) ranks P1 above P2, so it always runs
P1 first — for 5 units — before P2 gets a chance to even start, and P2 (due
at t = 6) doesn't finish until t = 7. DM (deadline-based) ranks P2 above P1,
runs the *tighter* deadline first, and both finish comfortably inside their
deadlines. Same two jobs, same total work, opposite order.

```
RM : t=0 P1 runs (priority: shorter period) -> finishes t=5 (deadline 9, OK)
     t=5 P2 finally runs -> finishes t=7  ***DEADLINE WAS 6 -- MISSED***

DM : t=0 P2 runs (priority: shorter deadline) -> finishes t=2 (deadline 6, OK)
     t=2 P1 runs -> finishes t=7 (deadline 9, OK)
```

**Result: exactly the textbook gap between the two policies.**

| | RM | DM | EDF |
|---|---|---|---|
| Feasible until | **t=6 (Process 2 misses)** | **entire 413-unit window** | **entire 500-unit window** |
| Total misses | 2 | **0** | **0** |
| CPU utilization | 80.2% | 78.5% | 77.8% |

This is the cleanest possible demonstration of *why* Deadline Monotonic
exists: RM's optimality among fixed-priority policies is only proven for
the case where every relative deadline equals its period; the moment a
process has a deadline meaningfully shorter than its period, RM's
period-only ranking can starve it, and DM's deadline-based ranking fixes
exactly that.

## Summary — answering the assignment's three questions

- **Can a feasible schedule be created?** Yes for EDF in every test here
  where total utilization ≤ 100% (custom_input3.txt, custom_input2_3.txt).
  DM also achieves a fully feasible schedule whenever RM's fixed period-only
  priority isn't the actual bottleneck (custom_input2_3.txt). RM was the only
  policy to fail on a workload (custom_input2_3.txt) that both DM and EDF
  handled without a single miss.
- **When does scheduling fail?** Always exactly when total utilization
  exceeds what the policy can guarantee: overload (>100%) breaks all three
  policies identically (sample_given3.txt); at exactly 100% utilization only
  EDF is theoretically guaranteed and is the only one that held
  (custom_input3.txt); and even well under 100% utilization, RM alone can
  still fail purely because of *how* it assigns priority when deadlines are
  shorter than periods (custom_input2_3.txt) — a failure mode DM was
  specifically designed to close.
- **CPU load/use:** reported per run above as both raw busy-time units and a
  percentage of the simulated horizon; an overloaded system pegs at 100%
  utilization for every policy (there's always more ready work than CPU
  time), while a well-provisioned system settles near its true total
  utilization once the schedule stabilizes.

########## rts_sim3.py ##########
"""
rts_sim3.py
----------
Operating Systems - Real-Time Scheduling Project

Implements a NEXT-EVENT (event-driven) simulator for three classic
real-time scheduling policies:

    RM  - Rate Monotonic          (fixed priority, shorter PERIOD = higher priority)
    DM  - Deadline Monotonic      (fixed priority, shorter RELATIVE DEADLINE = higher priority)
    EDF - Earliest Deadline First (dynamic priority, earliest ABSOLUTE deadline
                                    of a job currently in the system = highest priority)

All three are PREEMPTIVE: a higher-priority job that arrives while a
lower-priority job is running immediately takes over the CPU; the
preempted job's remaining service time is saved and it resumes later.

------------------------------------------------------------------------
WHY THIS FILE ADDS A "SERVICE TIME" COLUMN
------------------------------------------------------------------------
The assignment's input table only lists Process Number, Arrival Time,
Relative Deadline and Period. That is not enough information to schedule
anything: every one of RM/DM/EDF needs to know how long each job actually
executes (its service/execution time, usually written C_i in scheduling
literature) to decide who runs next or whether a deadline was met. The
assignment text itself acknowledges this ("this program doesn't specify
certain service times... following are some suggestions... in
milliseconds"), so a 5th column (ServiceTime) was added to the input file
format. See the two input files in this project for how that value was
chosen for the assignment's own sample vs. for our own custom test set.

------------------------------------------------------------------------
EVENT-DRIVEN SIMULATION DESIGN
------------------------------------------------------------------------
Rather than a fixed-timestep ("tick") simulation, the clock jumps directly
from one meaningful event to the next:
    - a new job (periodic task instance) ARRIVES, or
    - the currently running job COMPLETES.
Between events nothing about *who should be running* can change, so we
never need to inspect time in between. At every event the simulator:
    1. figures out which ready job has the highest priority under the
       policy being simulated,
    2. runs it until either the next arrival or its own completion,
       whichever comes first (this naturally implements preemption -- if
       a higher-priority job arrives before the current one finishes, the
       next loop iteration picks the new arrival instead),
    3. records completions and (crucially) deadline misses,
    4. repeats until the simulation horizon is reached.
"""

import heapq
from dataclasses import dataclass, field
from typing import List, Optional


# ---------------------------------------------------------------------------
# DATA MODEL
# ---------------------------------------------------------------------------

@dataclass
class ProcessDef:
    """Static definition of a periodic process, as read from the input file."""
    pid: int
    arrival: int          # first release time (assignment says: always 0)
    rel_deadline: int      # D_i - time allowed to finish AFTER release
    period: int             # T_i - time between successive releases
    service: int            # C_i - execution/service time per job (added column)


@dataclass
class Job:
    """One periodic *instance* (release) of a process -- what actually gets scheduled."""
    pid: int
    release_time: int
    abs_deadline: int
    service_time: int
    remaining: int
    finish_time: Optional[int] = None
    missed: bool = False
    miss_time: Optional[int] = None


def load_processes(path):
    """
    Parse an input file:
        line 1: "<num_processes> <process_switch_overhead>"
        lines 2..N+1: "<pid> <arrival> <rel_deadline> <period> <service>"
    Comment lines starting with '#' and blank lines are ignored.
    """
    processes = []
    switch_overhead = 0
    num_processes = 0
    header_seen = False
    with open(path) as f:
        for line in f:
            line = line.strip()
            if not line or line.startswith("#"):
                continue
            parts = line.split()
            if not header_seen:
                num_processes, switch_overhead = int(parts[0]), int(parts[1])
                header_seen = True
                continue
            pid, arrival, rel_deadline, period, service = map(int, parts)
            processes.append(ProcessDef(pid, arrival, rel_deadline, period, service))
    assert len(processes) == num_processes, (
        f"Header declared {num_processes} processes but {len(processes)} were listed"
    )
    return processes, switch_overhead


# ---------------------------------------------------------------------------
# PRIORITY FUNCTIONS -- this is literally the only difference between the
# three algorithms; everything else in the simulator is shared code.
# ---------------------------------------------------------------------------

def priority_key_rm(job, proc_by_id):
    """Rate Monotonic: fixed priority by PERIOD. Shorter period => smaller key => runs first."""
    return (proc_by_id[job.pid].period, job.pid)


def priority_key_dm(job, proc_by_id):
    """Deadline Monotonic: fixed priority by RELATIVE deadline. Shorter D_i => runs first."""
    return (proc_by_id[job.pid].rel_deadline, job.pid)


def priority_key_edf(job, proc_by_id):
    """Earliest Deadline First: dynamic priority by this job's own ABSOLUTE deadline."""
    return (job.abs_deadline, job.pid)


PRIORITY_FUNCS = {"RM": priority_key_rm, "DM": priority_key_dm, "EDF": priority_key_edf}


# ---------------------------------------------------------------------------
# SIMULATION ENGINE
# ---------------------------------------------------------------------------

def generate_arrivals(processes, horizon):
    """
    Pre-compute every job release for every process up to `horizon`.
    Per the assignment, arrival (first release) is always 0 regardless of
    algorithm; subsequent releases repeat every `period`.
    Returns a flat list of Job objects sorted by release_time.
    """
    jobs = []
    for p in processes:
        k = 0
        t = p.arrival
        while t < horizon:
            jobs.append(Job(
                pid=p.pid,
                release_time=t,
                abs_deadline=t + p.rel_deadline,
                service_time=p.service,
                remaining=p.service,
            ))
            k += 1
            t = p.arrival + k * p.period
    jobs.sort(key=lambda j: (j.release_time, j.pid))
    return jobs


def simulate(processes, switch_overhead, algorithm, horizon, log_lines):
    """
    Run one full event-driven simulation of `algorithm` (RM/DM/EDF) over
    [0, horizon). Returns a dict with feasibility/CPU-usage/per-process
    results ready to print or format into the assignment's report style.
    """
    proc_by_id = {p.pid: p for p in processes}
    priority_key = PRIORITY_FUNCS[algorithm]

    all_jobs = generate_arrivals(processes, horizon)
    arrival_idx = 0                 # pointer into all_jobs, sorted by release_time
    ready: List[Job] = []            # jobs that have arrived but not finished
    finished_jobs: List[Job] = []
    current_time = 0
    cpu_busy_time = 0
    switch_time_total = 0
    last_running_pid = None
    first_miss = None                # (time, pid) of the first deadline miss, if any

    def pull_arrivals_up_to(t):
        nonlocal arrival_idx
        while arrival_idx < len(all_jobs) and all_jobs[arrival_idx].release_time <= t:
            ready.append(all_jobs[arrival_idx])
            log_lines.append(
                f"t={all_jobs[arrival_idx].release_time:>4} | ARRIVE | "
                f"P{all_jobs[arrival_idx].pid} job released, "
                f"deadline={all_jobs[arrival_idx].abs_deadline}, "
                f"service={all_jobs[arrival_idx].service_time}"
            )
            arrival_idx += 1

    def check_deadline_misses(t):
        nonlocal first_miss
        for j in ready:
            if not j.missed and j.remaining > 0 and t > j.abs_deadline:
                j.missed = True
                j.miss_time = j.abs_deadline
                log_lines.append(
                    f"t={j.abs_deadline:>4} | MISS   | P{j.pid} missed its deadline "
                    f"(remaining={j.remaining} at deadline)"
                )
                if first_miss is None:
                    first_miss = (j.abs_deadline, j.pid)

    # jobs that arrive exactly at t=0
    pull_arrivals_up_to(0)

    while current_time < horizon:
        check_deadline_misses(current_time)
        ready[:] = [j for j in ready if j.remaining > 0]  # drop completed

        if not ready:
            # idle -- jump straight to the next arrival (event-driven: skip empty time)
            if arrival_idx >= len(all_jobs):
                break  # nothing left to do at all
            next_t = min(all_jobs[arrival_idx].release_time, horizon)
            current_time = next_t
            pull_arrivals_up_to(current_time)
            continue

        # pick the highest-priority ready job under this algorithm
        running = min(ready, key=lambda j: priority_key(j, proc_by_id))

        # context-switch overhead if the CPU is handing off to a different process
        if switch_overhead > 0 and last_running_pid is not None and last_running_pid != running.pid:
            overhead = min(switch_overhead, horizon - current_time)
            current_time += overhead
            switch_time_total += overhead
            cpu_busy_time += overhead
            log_lines.append(f"t={current_time:>4} | SWITCH | overhead={overhead} (P{last_running_pid}->P{running.pid})")
            check_deadline_misses(current_time)

        next_arrival_time = all_jobs[arrival_idx].release_time if arrival_idx < len(all_jobs) else horizon
        completion_time = current_time + running.remaining
        next_event_time = min(next_arrival_time, completion_time, horizon)

        elapsed = next_event_time - current_time
        if elapsed > 0:
            running.remaining -= elapsed
            cpu_busy_time += elapsed
            current_time = next_event_time
        else:
            # simultaneous arrival/completion at the same instant -- still must
            # advance to avoid an infinite loop; nothing to execute this tick
            current_time = next_event_time

        last_running_pid = running.pid

        if running.remaining <= 0 and running.finish_time is None:
            running.finish_time = current_time
            finished_jobs.append(running)
            late = current_time > running.abs_deadline
            log_lines.append(
                f"t={current_time:>4} | FINISH | P{running.pid} job "
                f"(released {running.release_time}) done "
                f"{'-- LATE' if late else '(on time)'} (deadline was {running.abs_deadline})"
            )
            if late and not running.missed:
                running.missed = True
                running.miss_time = running.abs_deadline
                if first_miss is None:
                    first_miss = (running.abs_deadline, running.pid)

        if current_time >= horizon:
            break
        pull_arrivals_up_to(current_time)

    check_deadline_misses(current_time)

    total_misses = sum(1 for j in all_jobs if j.missed) + sum(
        1 for j in finished_jobs if j.finish_time is not None and j.finish_time > j.abs_deadline and not j.missed
    )
    # (finished_jobs late ones are already flagged missed above; keep this simple/robust)
    total_misses = len({(j.pid, j.release_time) for j in all_jobs if j.missed})

    feasible_until = first_miss[0] if first_miss else horizon
    utilization_pct = 100.0 * cpu_busy_time / horizon if horizon else 0.0

    # per-process report: arrival, service, period, list of finish times
    per_process = []
    for p in processes:
        finishes = [j.finish_time for j in all_jobs if j.pid == p.pid and j.finish_time is not None]
        per_process.append({
            "pid": p.pid,
            "arrival": p.arrival,
            "service": p.service,
            "period": p.period,
            "rel_deadline": p.rel_deadline,
            "finishes": finishes,
            "missed_count": sum(1 for j in all_jobs if j.pid == p.pid and j.missed),
        })

    return {
        "algorithm": algorithm,
        "horizon": horizon,
        "feasible_until": feasible_until,
        "first_miss": first_miss,
        "total_misses": total_misses,
        "cpu_busy_time": cpu_busy_time,
        "switch_time_total": switch_time_total,
        "utilization_pct": utilization_pct,
        "per_process": per_process,
    }


# ---------------------------------------------------------------------------
# REPORT FORMATTING -- mirrors the style shown in the assignment prompt
# ---------------------------------------------------------------------------

def format_report(result):
    lines = []
    algo = result["algorithm"]
    lines.append(f"{algo} Results:")
    lines.append("")
    if result["first_miss"]:
        t_miss, pid_miss = result["first_miss"]
        lines.append(
            f"Schedule feasible from 0 to {result['feasible_until']} units. "
            f"At {t_miss}, process {pid_miss} did not meet deadline. "
            f"CPU time took {result['cpu_busy_time']} units "
            f"(simulated for {result['horizon']} units, "
            f"{result['utilization_pct']:.1f}% utilization, "
            f"{result['total_misses']} total deadline miss(es)."
        )
    else:
        lines.append(
            f"Schedule feasible for the entire simulated window (0 to {result['horizon']} units). "
            f"No deadlines missed. CPU time took {result['cpu_busy_time']} units "
            f"({result['utilization_pct']:.1f}% utilization)."
        )
    lines.append("")
    for pp in result["per_process"]:
        finishes_str = ", ".join(str(f) for f in pp["finishes"]) if pp["finishes"] else "(none completed)"
        miss_note = f"  [{pp['missed_count']} missed]" if pp["missed_count"] else ""
        lines.append(
            f"Process {pp['pid']}: Arrival Time: {pp['arrival']}, Service: {pp['service']}, "
            f"Relative Deadline: {pp['rel_deadline']}, Period: {pp['period']}, "
            f"finish: {finishes_str}.{miss_note}"
        )
    return "\n".join(lines)


# ---------------------------------------------------------------------------
# DRIVER
# ---------------------------------------------------------------------------

# Suggested simulation horizons from the assignment prompt (milliseconds)
HORIZONS = {"RM": 101, "DM": 413, "EDF": 500}


def run_all(input_path, out_path):
    processes, switch_overhead = load_processes(input_path)

    full_log = []
    full_log.append(f"INPUT FILE: {input_path}")
    full_log.append(f"Processes: {len(processes)}, switch overhead: {switch_overhead}")
    full_log.append("")

    results = {}
    for algo in ("RM", "DM", "EDF"):
        horizon = HORIZONS[algo]
        event_log = []
        result = simulate(processes, switch_overhead, algo, horizon, event_log)
        results[algo] = result

        # Events are appended in the order the simulator discovers them, which
        # is not always strict chronological order (e.g. a deadline-miss check
        # can log a miss at an earlier timestamp than a FINISH already printed
        # for a different job this same iteration). Stable-sort by the "t=NNN"
        # prefix so the printed trace reads top-to-bottom in real time order,
        # purely for readability -- it does not affect simulation results.
        def event_time(line):
            return int(line.split("|", 1)[0].strip().split("=")[1])
        event_log_sorted = sorted(event_log, key=event_time)

        full_log.append("=" * 78)
        full_log.append(f"{algo}  (simulated horizon = {horizon} units)")
        full_log.append("=" * 78)
        full_log.append("--- Event trace (sorted chronologically) ---")
        full_log.extend(event_log_sorted)
        full_log.append("")
        full_log.append("--- Summary ---")
        full_log.append(format_report(result))
        full_log.append("")

    with open(out_path, "w") as f:
        f.write("\n".join(full_log) + "\n")

    return results


if __name__ == "__main__":
    import sys
    in_path = sys.argv[1]
    out_path = sys.argv[2]
    run_all(in_path, out_path)
    print(f"Wrote {out_path}")

########## custom_input2_3.txt ##########
# Format: ProcessNumber ArrivalTime RelativeDeadline Period ServiceTime
# Header: NumberOfProcesses ProcessSwitchOverhead
#
# Second custom process set - engineered specifically to make RM fail where
# DM succeeds, demonstrating the textbook gap between the two policies.
#
# Process 1: period=10 (shorter than P2's), deadline=9, service=5
# Process 2: period=12 (longer than P1's), deadline=6 (much TIGHTER), service=2
#
# RM ranks purely by period -> P1 (period 10) beats P2 (period 12), so RM
# always runs P1 first. At t=0 both arrive; RM runs P1 for 5 units (0->5,
# meets its own deadline of 9 fine), THEN P2 for 2 units (5->7) -- but P2's
# deadline was 6, so P2 is already late. RM's own priority assignment causes
# the miss.
